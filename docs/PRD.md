**버전** v1.3 · **작성일** 2026-08-20 · **최종 수정** 2026-08-28 · **대상 축제** 6단대 연합 축제 GROOVE (IT × 간호 × 예술 × 사회 × 사범 × 자연)

## 0. 문서 목적

이 문서는 GROOVE 축제 사이트의 5대 서비스(주막 지도/QR 주문, 가요제 투표·사연받기, 기획 페이지/라이벌스, GROOVE PLAYLIST, 관리자 대시보드)에 대한 요구사항, 사용자 흐름, 정보구조, 데이터 모델을 정의한다. Figma 디자인 작업과 개발 작업의 기준 문서로 사용한다.

## 4. 기능 요구사항

### 4.0 메인 화면

- FR-0.1 첫 진입 화면(히어로)은 로고, 참여 단대 목록(IT × 간호 × 예술 × 사회 × 사범 × 자연), 축제 일정(2026.10.01. – 10.02.), 슬로건 문구("우리의 밤은 당신의 낮보다 아름답다")로 구성한다.
- FR-0.2 히어로 영역은 최초 진입 시 스크롤 없이 보이는 화면(첫 화면 전체)을 채우도록 구성한다. "축제 전체 지도" 섹션은 이 히어로 아래(스크롤 후 영역)에 위치한다.
- FR-0.3 "축제 전체 지도" 미리보기 아래에 [전체 / 주막 / 이벤트 부스] 필터 버튼을 배치해, 지도 위에 표시되는 마커 종류를 전환할 수 있게 한다.
  - 전체: 주막 마커 + 이벤트 부스(체험존) 마커 모두 표시
  - 주막: 주막 마커만 표시
  - 이벤트 부스: 체험존(§4.3 기획 페이지의 zone) 마커만 표시
  - 지도를 탭하면 현재 필터에 따라 주막 지도(§4.1) 또는 기획 페이지 지도(§4.3)로 이동한다.
- FR-0.4 사연 모집이 켜져 있는 동안에는 홈 화면의 가요제 배너에 "사연 모집중" 알림 배지가 노출된다.

### 4.1 주막 지도 + QR 셀프 주문 서비스

**URL 구조**
- **주막 정보 페이지** (로그인 없음): `/pub/{boothCode}` — 메뉴판 사진과 메뉴 리스트만 확인 (주문 불가). 지도·목록에서 주막을 탭하면 이 페이지로 이동한다.
- **주문 페이지** (로그인 없음): `/pub/{boothCode}/{tableCode}` — 테이블에 부착된 QR을 스캔해야만 도달하는 실제 주문 화면. `{tableCode}`는 예측 불가능한 랜덤 문자열.
- **관리자용** (로그인 필요): `/pub/admin/{boothId}`

일반 탐색(지도·목록)에서는 메뉴 정보만 보여주고, 실제 주문은 테이블 QR을 스캔했을 때만 가능하다. 손님이 테이블에 앉기 전에 미리 메뉴를 확인할 수 있으면서도, 다른 테이블 번호를 추측해 엉뚱한 곳에 주문을 넣는 상황을 방지한다.

**결제 방식 (v1.3 확정)**

운영팀 회신에 따라 **입금자명 제출 기반 수기 대사** 방식으로 확정했다. 알바생이 테이블마다 찾아가 입금 화면을 눈으로 확인하던 방식(직원이 언제 올지 모름 / 좁은 테이블을 하나하나 확인 / 확인 전까지 조리가 시작되지 않음 / 입금 화면이 진짜라는 증거 확보 어려움)의 문제를 없애고, 계좌 주인 1명이 관리자 페이지에서 입금 내역과 대조해 일괄 승인하는 구조다.

```
① 손님: QR 스캔 → 메뉴 담기 → 주문하기
② 손님: 주문 완료 모달에서 계좌번호 복사 → 뱅킹 앱에서 계좌이체
③ 손님: 모달로 돌아와 이체할 때 쓴 입금자명을 입력·제출   → 상태 `입금확인중`
④ 관리자: 관리자 페이지의 입금자명·금액을 실제 입금 내역과 대조 → `결제완료` → 조리 시작
```

이 흐름은 일반 참여자에게 익숙하지 않으므로, **주의사항 팝업·주문 페이지 상단 안내·주문 완료 모달의 단계 인디케이터 세 곳에서 반복해 안내한다**(운영팀이 명시적으로 요청한 사항, FR-1.0 / FR-1.3-1 / FR-1.4-1).

**참여자(손님) — 주막 정보 페이지 (`/pub/{boothCode}`)**
- FR-1.0 주막 목록/지도 진입 시, 처음 한 번 주막 이용 주의사항 팝업(음주 관련 유의사항 등)을 노출한다. 이 팝업에는 **계좌이체 결제 흐름 요약(주문 → 계좌번호 복사·이체 → 입금자명 제출 → 관리자 확인 후 조리 시작)** 을 함께 담는다.
- FR-1.0-1 주막을 위치 구역(학생주차장 / 러브로드) 버튼으로 먼저 선택한 뒤, 해당 구역의 지도·단과대학 목록을 본다.
- FR-1.1 구역 지도 위에 주막 위치를 마커로 표시한다.
- FR-1.2 주막을 탭하면 주막 정보 페이지로 이동해 메뉴판 사진과 메뉴 리스트(이름·가격·품절 여부)만 확인한다. 수량 선택이나 장바구니 등 주문 관련 UI는 이 페이지에 없다.
- FR-1.2-1 주막 목록 카드는 단대 배지 + 학과(부스)명만 표시한다.
- FR-1.2-2 하나의 주막을 두 개 단과대학이 공동 운영하는 "연합 부스"가 있을 수 있다. 연합 부스는 관련된 양쪽 단과대 필터 모두에서 노출된다 (지도·목록·홈 미리보기 공통 적용).

**참여자(손님) — 주문 페이지 (`/pub/{boothCode}/{tableCode}`, 테이블 QR 스캔 시에만 도달)**
- FR-1.3 QR 스캔으로 접속하면 로그인 없이 메뉴판 사진과 터치 주문 가능한 메뉴 표를 확인한다.
  - 주막이 **준비중** 상태이면 메뉴판 사진만 노출하고, 주문 UI(수량 선택·담기·주문하기)는 비활성화된다.
  - 주막이 **오픈** 상태이면 메뉴 담기 + 주문 제출이 가능하다.
- FR-1.3-1 주문 페이지 상단에는 결제 흐름 안내를 **팝업이 아닌 고정 영역으로 상시 노출**한다. "주문만 하면 끝"이라고 오해하지 않도록 ① 주문하기 → ② 계좌번호 복사 후 이체 → ③ 입금자명 제출 → ④ 관리자 입금 확인 후 조리 시작 4단계를 문장·아이콘으로 명시한다.
- FR-1.4 메뉴별 수량을 선택해 장바구니에 담고 "주문하기"를 누르면 주문이 접수된다.
- FR-1.4-1 주문 제출 시 **주문 완료 모달**이 뜨며 다음을 보여준다: 주문 접수 문구, 주막명·주문 내역·결제 금액, 대표자 계좌번호(은행명·계좌번호·예금주), 클립보드 복사 버튼, 그리고 지금 어느 단계인지 알려주는 **진행 인디케이터(① 계좌이체 → ② 입금자명 제출 → ③ 입금 확인 대기)**.
- FR-1.4-2 손님은 계좌이체를 마친 뒤 **같은 모달에서 입금자명을 입력해 제출**한다. 제출하면 주문 상태가 `입금대기` → `입금확인중`으로 바뀌고 "입금이 확인되면 조리가 시작돼요" 안내가 표시된다. 입금자명은 필수 입력이며, **실제 이체에 사용한 이름과 똑같이 적어야 한다**는 문구를 입력창 옆에 함께 노출한다.
- FR-1.4-3 입금자명은 관리자가 결제완료로 전환하기 전까지 손님이 수정·재제출할 수 있다 (이름을 잘못 적었을 때의 복구 수단).
- FR-1.4-4 모달을 실수로 닫았거나 이체를 마치고 다시 들어온 경우를 위해, 같은 테이블 주문 페이지 상단에 **"입금자명 제출하기" 배너**를 노출해 방금 넣은 주문의 모달로 다시 들어갈 수 있게 한다. 주문 식별은 브라우저에 저장된 주문 토큰으로 처리하며 로그인은 요구하지 않는다 (§11-18).
- FR-1.4-5 현장 현금 결제도 병행 가능하다. 현금으로 낸 손님은 입금자명을 제출하지 않으며, 주막 관리자가 관리자 화면에서 해당 주문을 직접 결제완료로 전환한다.
- FR-1.5 같은 테이블에서 여러 차례 추가 주문이 가능하다. 주문 건마다 계좌이체·입금자명 제출을 각각 수행한다.
- FR-1.6 손님 화면에는 전체 주문 이력 페이지를 두지 않는다. 다만 **현재 테이블에서 이 브라우저로 넣은 주문에 한해** 상태(`입금대기` / `입금확인중` / `결제완료`)를 주문 완료 모달과 상단 배너에서 확인할 수 있다. 손님은 주문을 스스로 취소할 수 없다.

**주막 관리자**
- FR-1.7 `/pub/admin/{boothId}`에 로그인하면 본인 주막으로 들어온 주문을 실시간 리스트로 확인한다.
- FR-1.8 주문 상태를 `입금대기` → `입금확인중` → `결제완료` → `완료` 순서로 변경하며, 필요 시 취소 처리한다. **`결제완료`가 조리 착수 신호**이고, `완료`는 서빙까지 끝난 상태다. `입금확인중`은 손님이 입금자명을 제출하면 자동으로 전환된다.
- FR-1.8-1 주문 리스트에는 손님이 제출한 **입금자명·결제 금액·주문 시각**이 함께 표시된다. 관리자는 자기 계좌의 실제 입금 내역(뱅킹 앱)에서 같은 이름·금액의 송금 건을 확인한 뒤 `결제완료`로 전환한다. **사이트가 은행 계좌를 직접 조회해 자동 대사하지는 않는다.**
- FR-1.8-2 `입금확인중` 주문은 리스트 상단에 모아 보여주고, 입금자명이 아직 제출되지 않은 `입금대기` 주문과 시각적으로 구분한다. 동명이인·동일 금액이 겹칠 수 있으므로 주문 시각을 함께 노출해 구분할 수 있게 한다 (§11-17).
- FR-1.9 메뉴를 등록·수정하고, 대표 메뉴판 사진 1장을 업로드·교체한다.
- FR-1.10 주막 상태를 오픈 / 준비중으로 토글한다.
- FR-1.11 대표자 계좌번호(은행명 + 계좌번호 + 예금주)를 등록·수정한다. 등록된 계좌번호는 주문 완료 팝업에 복사 가능한 형태로 노출된다.

### 4.2 가요제 (투표 + 사연받기)

가요제는 GPS 범위 내/외 구분과 별개로 축제 시작 전/후 구분이 필요하다. 시작 전에는 투표가 존재하지 않고 사연받기만 운영되며, 시작 후에는 사연받기 없이 투표만 운영된다. 타임테이블/투표 목록은 두 단계 모두 동일하게 노출되고, 하나의 카드 안에서 슬라이드(세그먼트) 버튼으로 두 뷰를 전환한다.

가요제 투표는 사전에 정의된 대진표 구조를 따르지 않는다. 무대팀 관리자가 진행 상황에 맞춰 투표를 직접 생성하며, 생성 시 제목·참가자·종료 시간을 입력한다. 참가자 수는 2명 이상 자유롭게 추가할 수 있다.

**공통 (시작 전/후 모두)**
- FR-2.0-1 가요제 페이지 상단에 타임테이블 / 투표 목록을 확인한다. 두 뷰는 같은 영역에서 슬라이드 버튼(세그먼트 컨트롤)으로 전환되며, 화면 전환(페이지 이동)은 발생하지 않는다.
  - 타임테이블: 당일 진행 시간 안내용 리스트 (예선/결선 등 대략적인 시간표, 실제 투표 생성과는 별개의 정보성 콘텐츠)
  - 투표 목록: 무대팀 관리자가 생성한 투표들의 목록 — 각 투표의 제목, 참가자, 오픈/마감 상태, 남은 시간을 보여준다 (§8 SingingVote 엔티티 참고)

**사전 단계 (가요제 시작 전)**
- FR-2.0 참여자는 가요제 시작 전 사연받기 폼에 [단대, 학과, 학번, 이름, 별명(선택), 본문]을 입력해 사연을 제출한다 (신청곡과는 별개의 엔티티).
  - 별명은 선택 입력 항목이며, 입력 시 무대에서 MC가 사연을 소개할 때 본명 대신(또는 병기하여) 불러줄 수 있는 이름으로 활용한다. 미입력 시 본명만 사용한다.
  - 사연 제출에는 Google OAuth 로그인이 필요하다 (가요제 투표와 동일 인증 방식 재사용, 계정 기준 어뷰징 방지). GROOVE PLAYLIST는 v1.3부터 학번 로그인으로 분리됐으므로 인증 체계를 공유하지 않는다.
  - 사연받기 폼은 무대팀 관리자가 사연 모집을 켰을 때(on)만 노출된다. 꺼져 있으면(off) 폼 대신 "사연 모집이 아직이에요" 안내만 보여준다.
- FR-2.0-2 접수된 사연은 팝업이 아니라 가요제 페이지 내 알림(배너/토스트류 UI)로 노출되며, 실제 활용처는 무대 진행 중 MC가 낭독하는 이벤트성 콘텐츠다. 투표/득표에는 영향을 주지 않는다.
- FR-2.0-3 축제 시작 전에는 투표 UI가 노출되지 않는다 (사연받기 폼만 표시).
- FR-2.0-4 사연 모집이 켜져 있는 동안에는 홈 화면의 가요제 배너와 상단 메뉴 목록의 가요제 항목에 "사연 모집중" 알림 배지가 노출된다.

**가요제 시작 후**
- FR-2.1 GPS 기준으로 행사장 반경 N m 이내일 때만 투표 카드가 활성화된다 (기본값 100m). 반경 밖이면 안내 화면만 노출되고 투표 카드는 보이지 않는다.
- FR-2.2 가요제 투표는 투표(경기) 단위로 진행되며, 각 투표는 무대팀 관리자가 미리 만들어 둔 참가자 카드로 보여준다.
  - 참가자가 2명이면 좌우 대결(VS) 카드로, 3명 이상이면 세로로 나열된 목록 카드로 표시한다.
  - Google OAuth 로그인 후, 현재 오픈된 투표에 한해 투표할 수 있다 (계정 기준 1인 1투표/경기).
- FR-2.2-1 참가자를 탭하면 확인 팝업이 뜨며 "OO에게 투표하시겠어요? 투표 후에는 수정할 수 없어요." 문구와 확정/취소 버튼을 보여준다. 팝업에서 확정을 눌러야 실제 투표가 반영된다.
- FR-2.2-2 투표가 확정된 경기는 수정이 불가능하다 (다시 탭해도 반응하지 않음).
- FR-2.3 투표를 마친 경기는 같은 페이지 하단의 "완료된 투표" 영역으로 이동해 카드 형태로 계속 노출된다. 카드에는 "완료된 투표" 라벨과 함께 본인이 선택한 참가자가 강조 표시된다 (선택하지 않은 참가자는 흐리게 표시).
- FR-2.4 타임테이블 / 투표 목록은 시작 후에도 계속 동일하게 노출된다 (공통 영역, FR-2.0-1).
- FR-2.9 "가요제 투표 결과" 화면은 전체 참가자를 하나로 합산하지 않고, 투표(경기)별로 득표 현황을 나눠서 보여준다.

**무대팀 관리자**
- FR-2.5 사연 모집을 켜고 끄며(on/off), 접수된 사연 목록을 확인한다.
- FR-2.5-1 접수된 사연에 대한 별도의 "낭독 완료 체크" 기능은 없다. 관리자는 필요 시 사연을 삭제할 수 있다.
- FR-2.6 경기(투표)를 오픈/마감한다.
- FR-2.6-1 관리자는 투표를 직접 생성할 수 있다. 생성 시 입력 항목은 투표 제목, 참가자 이름(2명 이상, "참가자 추가" 버튼으로 인원 자유 추가), **몇 분 뒤 종료할지(분 단위)**이다. 생성된 투표는 기본적으로 "오픈" 상태로 추가되며, 종료 시각은 생성 시점 기준으로 자동 계산된다.
- FR-2.7 경기(투표)별 득표 현황을 조회한다.
- FR-2.8 관리자 페이지에서 GPS 허용 반경을 설정한다 (기본값 100m).
- FR-2.8-1 GPS 허용 반경 설정 UI 위에 반경을 원으로 시각화하는 미리보기를 함께 보여줘, 슬라이더 값이 실제로 어느 정도 범위인지 감을 잡을 수 있게 한다 (실제 지도 좌표 연동이 아닌 상대적 크기 비교용 시각 자료).

### 4.3 기획 페이지 (라이벌스)

- FR-4.1 체험존/부스 위치를 지도에서 확인한다.
- FR-4.2 각 부스를 클릭하면 부스 설명(카드뉴스 형태로 연결)을 확인한다.
- FR-4.3 단대 순위표를 확인한다. 점수는 기획팀 자체 이벤트 운영 결과에 따라 기획팀이 수동으로 입력하며, 사이트는 입력된 점수를 등수와 함께 보여주기만 한다 (별도의 자동 산정 로직 없음).

**기획팀 관리자**
- FR-4.4 단대별 현재 라이벌스 점수를 확인하고, 추가할 점수를 입력해 누적한다 (기존 점수를 덮어쓰는 것이 아니라 더하는 방식).

> 참고: 라이벌스 순위는 GROOVE PLAYLIST(§4.4)와는 완전히 별개의 지표다. GROOVE PLAYLIST는 순위·집계가 없는 신청곡 리스트이고, 라이벌스는 기획팀이 수기로 매기는 종합 점수다.

### 4.4 GROOVE PLAYLIST

> **개발 우선순위**: GROOVE PLAYLIST는 **9/12**부터 신청을 받는 기능이므로, 다른 서비스보다 먼저 개발되어 **9/10까지 배포·실사용 가능한 상태**가 되어야 한다. 개발 착수 시 이 섹션을 최우선으로 검토할 것.

> **v1.3 변경 요약 (운영팀 회신 반영)**: ① 인증이 Google OAuth → **학번 로그인**으로 바뀌었다. ② 같은 학번으로 다시 신청하면 **기존 곡을 덮어쓴다**(학번당 최종 1곡). ③ 신청 기간에는 **다른 사람이 무엇을 신청했는지 보여주지 않는다** — 구글폼과 동일한 경험. ④ 축제 기간에는 **운영팀이 고른 최종 곡 목록만** 공개한다. 목록을 감추는 이유는 곡 선정을 운영팀이 직접 하기 때문이며, 이 결정 때문에 v1.2의 "선착순 중복 곡 차단"은 폐기된다.

GROOVE PLAYLIST는 순위를 매기는 "차트"가 아니라, 참여자들이 신청한 곡 중에서 운영팀이 축제 플레이리스트를 완성하는 기능이다. 좋아요·추천·순위 집계 기능은 두지 않는다.

신청 시에는 유튜브뮤직에서 실제로 존재하는 곡만 검색해 선택할 수 있으며(제목·아티스트·앨범 커버 자동 반영), 임의의 텍스트 입력으로는 등록할 수 없다.

**서비스 단계**

곡 신청은 사전 접수 기간에만 열리고, 목록 공개는 축제 기간에만 이루어진다. 네 단계에서 화면이 완전히 달라진다.

| 단계 | 기간 | 참여자 화면 |
|---|---|---|
| ① 오픈 전 | ~ 9/11 | "곧 신청이 열려요" 안내 + 오픈 일시. 신청 폼·목록 모두 없음 |
| ② 신청 접수 | **9/12 – 9/16** | 학번 로그인 후 신청 폼. **타인의 신청 목록 비노출.** 본인이 신청한 곡만 확인·변경 가능 |
| ③ 선정 기간 | 9/17 – 9/30 | "신청이 마감됐어요. 최종 플레이리스트는 축제 기간에 공개됩니다" 안내. 목록 비공개 유지 |
| ④ 공개 | **10/1 – 10/2** | 운영팀이 선정한 **최종 곡 목록**만 열람 (로그인 불필요, 열람 전용) |

**② 신청 접수 기간 (9/12 – 9/16)**
- FR-3.0 곡 신청에는 **학번 로그인**이 필요하다. GROOVE PLAYLIST에서는 Google OAuth를 사용하지 않는다 (가요제 투표·사연은 기존대로 Google OAuth 유지).
- FR-3.0-1 로그인은 학번을 입력해 진행하며, 로그인한 학번이 곧 신청의 식별자가 된다. 학번만으로는 본인 확인이 되지 않는 문제(타인 학번 도용)에 대한 추가 방어 수준은 §11-13에서 확정한다.
- FR-3.1 신청 폼은 ① 유튜브뮤직 곡 검색·선택(제목·아티스트·앨범 커버 자동 반영), ② 단과대학·학과·이름 입력으로 구성된다. 학번은 로그인 값으로 자동 채워지며 수정할 수 없다.
  - 이름·학번·학과는 신원 확인·이상 신청 방지용으로 서버에 저장되며 홍보팀 관리자만 조회한다.
  - 닉네임은 최종 목록에 신청자를 표기할지 확정되기 전까지 **선택 입력** 항목으로 둔다 (§11-14).
- FR-3.2 **한 학번은 항상 1곡만 가진다.** 이미 신청한 학번이 다시 신청하면 확인 팝업("이미 신청한 곡이 있어요. 새로 고른 곡으로 바꿀까요?")을 거쳐 **기존 신청을 새 곡으로 덮어쓴다.** 신청 이력을 여러 건 쌓지 않고 학번당 최신 1건만 유효한 신청으로 유지한다.
- FR-3.2-1 로그인 후 신청 화면에 들어가면 본인이 이전에 신청한 곡이 먼저 보이고, "곡 변경하기" 버튼으로 다시 검색해 교체할 수 있다.
- FR-3.2-2 **다른 사람이 이미 같은 곡을 신청했더라도 신청을 막지 않는다.** 중복 여부를 알려주면 타인의 신청 내역이 간접적으로 드러나므로 중복 검사·선착순 차단을 두지 않는다. 중복 곡 정리는 운영팀의 최종 선정 단계에서 처리한다.
- FR-3.3 **신청 기간 중에는 참여자에게 신청 목록을 노출하지 않는다.** 총 신청 곡 수, 최근 신청 곡, 인기곡 등 다른 사람의 신청 내용을 유추할 수 있는 정보도 함께 노출하지 않는다. UI에서 숨기는 수준이 아니라 참여자용 API에서 조회 자체가 불가능해야 한다 (§10).
- FR-3.3-1 신청 후 참여자가 보는 화면은 "신청이 접수됐어요" + 본인이 신청한 곡 카드 + "곡 변경하기" 버튼까지다.

**③ 선정 기간 (9/17 – 9/30)**
- FR-3.4 신규 신청·곡 변경 모두 받지 않으며 신청 폼과 곡 검색 UI는 노출되지 않는다. "신청이 마감됐어요. 최종 플레이리스트는 축제 기간에 공개됩니다" 안내만 노출한다.
- FR-3.4-1 이 기간 동안 홍보팀 관리자가 신청 목록을 검토해 최종 곡을 선정한다 (FR-3.7).

**④ 공개 (10/1 – 10/2)**
- FR-3.5 운영팀이 선정한 **최종 곡 목록**을 열람 전용으로 공개한다. 로그인은 필요하지 않다.
- FR-3.5-1 목록에는 앨범 커버, 곡명, 아티스트를 표시한다. 신청자 정보(닉네임·단대) 표기 여부는 §11-14에서 확정한다.
- FR-3.5-2 순위·좋아요·투표 UI는 두지 않으며, 정렬은 운영팀이 지정한 공개 순서(플레이리스트 재생 순서)를 따른다.
- FR-3.5-3 선정되지 않은 신청 곡은 이 화면에 노출되지 않는다.

**홍보팀 관리자**
- FR-3.6 신청 명단을 단대별로 그룹핑해 조회한다. 각 항목에 학번·이름·학과·곡 정보·최종 수정 시각이 표시되며, 곡을 변경한 신청은 최신 값만 보인다.
- FR-3.7 신청 항목별로 **최종 선정 여부를 토글**하고 선정된 곡의 **공개 순서**를 지정한다. 선정 결과가 그대로 축제 기간 공개 목록(FR-3.5)이 된다.
- FR-3.8 서비스 단계(오픈 전 / 접수 / 선정 / 공개)를 관리자 화면에서 전환한다. 일시 기준 자동 전환으로 할지 수동 토글로 할지는 §11-16에서 확정한다.
- FR-3.9 부적절한 신청 항목을 삭제한다.
- FR-3.10 최종 목록을 축제 인스타그램 계정에 게시하는 작업은 운영진이 사이트 밖에서 수동으로 진행한다 (사이트 기능 범위 아님).

## 10. 비기능 요구사항 (NFR)

- 모바일 퍼스트, 실시간성, GPS 정확도, 개인정보 처리, OAuth 스코프 최소화, 관리자 보안, URL 추측 방지, 이미지 최적화, 동시 접속 대응
- **배포 경로**: 서비스는 `chcse.knu.ac.kr/groove` 하위 경로로 배포된다. 프론트엔드 라우터의 base path, 정적 자산 경로, 쿠키·세션 path, QR에 인코딩되는 절대 URL을 모두 `/groove` 기준으로 맞춰야 한다. 루트 도메인 기준으로 개발한 뒤 나중에 서브 경로로 옮기면 자산 경로·쿠키 스코프에서 문제가 생기므로, 로컬 개발 환경부터 같은 base path를 사용한다.
- **신청 목록 비공개 (GROOVE PLAYLIST)**: 신청 기간 중 타인의 신청 내역은 UI에서 숨기는 수준이 아니라 **참여자용 API에서 조회 자체가 불가능**해야 한다. 총 신청 수·중복 여부 응답 등 내용을 간접적으로 유추할 수 있는 정보도 내려주지 않는다. 신청 목록 조회는 홍보팀 관리자 인증이 필요한 엔드포인트로만 제공한다.
- **학번 로그인의 보안 한계**: 학번은 비밀값이 아니므로, 학번만 알면 타인 명의로 로그인해 그 사람의 신청 곡을 덮어쓸 수 있다. 최소한의 방어(로그인·신청 요청 rate limit, 신청 변경 이력 로깅, 동일 IP 다계정 탐지)를 적용하고, 추가 본인 확인 수단은 §11-13에서 확정한다.
- **입금자명 처리**: 입금자명은 실명일 가능성이 높은 개인정보다. 해당 주막 관리자만 조회할 수 있어야 하고, 축제 종료 후 정산이 끝나면 파기 대상에 포함한다.
- **결제 흐름 안내 필수**: 계좌이체 + 입금자명 제출은 손님에게 익숙하지 않은 흐름이므로, 주의사항 팝업(FR-1.0) · 주문 페이지 상단 고정 안내(FR-1.3-1) · 주문 완료 모달의 진행 인디케이터(FR-1.4-1) 세 곳에서 반복해 안내한다. 운영팀이 명시적으로 요청한 요구사항이다.
- **주문 토큰 보안**: 손님이 로그인 없이 자기 주문 모달에 다시 접근하는 수단이므로, 주문토큰은 예측 불가능해야 하고 해당 주문 1건에만 접근 권한을 준다 (다른 주문·다른 테이블 조회 불가).
- **외부 API 의존성**: GROOVE PLAYLIST는 곡 신청 시 검색·앨범 커버 조회를 위해 유튜브뮤직 API(또는 대체 음원 메타데이터 API) 연동에 의존하며, 검색 결과는 실제로 존재하는 곡으로만 제한된다(자유 텍스트 입력 없음). API 쿼터 초과·장애 시의 폴백 UI(검색 결과 없음 안내, 앨범 커버 기본 이미지 대체)를 설계 단계에서 함께 정의해야 한다. 접수 기간(9/12–9/16)에 트래픽이 집중되므로 쿼터 산정도 이 기간 기준으로 한다.
- **개인정보 최소 노출**: 신청곡의 본명·학번·학과는 홍보팀 관리자만 조회 가능한 비공개 정보로 서버에 저장하고, 축제 기간 공개 목록에는 곡 정보만 노출한다 (신청자 표기 여부는 §11-14).
- **계좌번호 노출 보안**: 계좌번호는 민감정보는 아니지만, 주막 관리자만 수정 가능하도록 하고 손님 화면에는 읽기 전용 + 복사 기능만 제공한다.
- **사연 콘텐츠 검수**: 무대에서 낭독되는 콘텐츠이므로, 무대팀 관리자가 사전에 검수(부적절한 내용 확인 후 필요 시 삭제)할 수 있는 최소한의 관리 기능이 필요하다.

## 11. 오픈 이슈 (기획 확정 필요 항목)

> ✅ 는 축제 운영팀 회신(2026-08-28)으로 v1.3에서 확정된 항목, 🆕 는 v1.3에서 새로 생긴 항목이다. API 명세서가 이슈 번호를 참조하고 있으므로 기존 번호(1–12)는 재배치하지 않고 신규 항목만 13번부터 붙인다.

1. **주막 구역(학생주차장/러브로드) 배치 기준** — 단대별로 구역이 고정되는지, 혹은 주막 종류에 따라 배치되는지 확정 필요.
2. **"모공" 학과명 확인** — 정확한 학과명이 불명확해 IT융합대학 계열로 임시 배정함. 정확한 명칭 확인 필요.
3. **"지리" 중복 표기 확인** — 사범대학(지리교육과)과 사회과학대학(지리학과) 두 개로 분리했는데, 실제로 맞는 구분인지 확인 필요.
4. **주문 상태 표기** — v1.3에서 상태가 `입금대기 / 입금확인중 / 결제완료 / 완료`로 늘어났다. 손님 화면과 관리자 화면에 노출할 최종 문구 확정 필요 (예: 손님에게는 "입금 확인 중이에요", 관리자에게는 "입금확인중").
5. **사연 제출 개수 제한** — 계정당 1건으로 제한할지, 여러 건 허용할지 확정 필요.
6. ✅ **중복 곡 판별 기준** — **확정: 신청 단계에서는 중복을 판별하지 않는다.** 신청 목록을 비공개로 두기로 한 이상 "이미 있는 곡입니다" 안내가 타인의 신청 내용을 노출하게 되므로, 중복 곡도 그대로 접수하고 운영팀이 최종 선정 단계에서 정리한다 (FR-3.2-2).
7. **유튜브뮤직 API 연동 범위** — 곡 검색·제목/아티스트/앨범커버 조회 및 실제 존재하는 곡만 검색되도록 제한하는 것까지는 확정. 실제 재생(미리듣기)까지 지원할지, 검색 결과가 없는 곡(비공식 음원 등)의 처리 방식은 API 정책·쿼터 확인 후 확정 필요.
8. **라이벌스 점수 가산 이력 저장 여부** — 누가 언제 몇 점을 더했는지 이력을 별도로 저장할지 확정 필요.
9. **사연받기 Google 로그인 요구 여부** — 가요제 사연·투표는 v1.3에서도 Google OAuth를 유지한다(GROOVE PLAYLIST만 학번 로그인으로 분리). 사연받기는 어뷰징 우려가 상대적으로 낮아 로그인 없이 받을지 재검토 필요.
10. **투표 참가자의 단대 소속 표기 여부** — 현재 무대팀 관리자가 투표 생성 시 참가자 이름을 자유 텍스트로만 입력하며, 특정 College/Team에 공식적으로 연결되지 않는다. 참가자 옆에 단대 소속을 표시할 것인지, 표시한다면 관리자가 어떻게 지정할지 확정 필요.
11. **투표 종료 시간의 자동 마감 여부** — 관리자가 투표 생성 시 몇 분 뒤 종료할지 입력하지만, 현재는 정보 표시용일 뿐 종료 시간이 지나도 자동으로 마감되지 않고 관리자가 수동으로 "투표 마감하기"를 눌러야 한다. 종료 시간 도달 시 자동 마감할지 확정 필요.
12. **사연 삭제의 영구성** — 무대팀 관리자가 사연을 삭제하면 복구 수단이 없다. 삭제 전 확인 절차(예: "정말 삭제하시겠어요?" 확인창)를 추가할지 확정 필요.
13. 🆕 **학번 로그인의 본인 확인 수단** — 학번은 알아내기 쉬운 값이라, 학번만으로 로그인하면 타인 명의로 신청 곡을 덮어쓸 수 있다. (a) 학번만 입력 (b) 학번 + 이름 일치 확인 (c) 학번 + 생년월일 등 추가 정보 (d) 학교 계정 인증 중 어느 수준으로 갈지 운영팀과 확정 필요. **v1.3 기본안은 (a)** 이며, 최소한 rate limit과 변경 이력 로깅은 적용한다. 신청 마감 직전 장난성 덮어쓰기 위험이 있으므로 접수 오픈(9/12) 전에 결론이 필요하다.
14. 🆕 **최종 목록의 신청자 표기 여부** — 축제 기간 공개 목록에 곡 정보만 보여줄지, 신청자(닉네임·단대)까지 붙일지 확정 필요. 표기하지 않기로 하면 신청 폼의 닉네임 입력 항목은 삭제한다. (디자인 시안 확정 전 필요)
15. 🆕 **최종 곡 선정 UI 범위** — 관리자 페이지에서 항목별 토글 + 공개 순서 지정까지 제공할지, 운영팀이 외부(엑셀 등)에서 고른 결과를 관리자가 등록만 할지 확정 필요. 최종 곡 수 상한도 함께 확정.
16. 🆕 **단계 전환 방식과 정확한 일시** — 접수 기간 9/12–9/16, 공개 10/1–10/2로 확정됐으나 정확한 오픈·마감 시각(예: 9/12 00:00 / 9/16 23:59)과, 단계 전환을 일시 기준 자동으로 할지 관리자 수동 토글로 할지 확정 필요. (축제 전체 단계 전환 방식과 함께 결정)
17. 🆕 **입금 대사 예외 처리** — 동명이인·동일 금액이 겹치는 경우, 주문 금액과 다르게 입금된 경우, 오래 입금이 확인되지 않는 주문의 자동 취소 기준(예: N분 경과) 확정 필요.
18. 🆕 **손님의 주문 재조회 수단** — 주문 완료 모달을 닫은 손님이 입금자명을 제출하러 돌아오는 경로. v1.3 기본안은 브라우저에 저장한 주문 토큰 기반 배너이며, 브라우저를 바꾸거나 시크릿 모드를 쓴 경우의 대안(주문번호 입력 등) 확정 필요.
19. 🆕 **신청 명단의 활용 범위** — 이름·학번·학과를 수집하는 목적(상품 지급·본인 확인)과 축제 종료 후 파기 시점을 운영팀과 문서로 확정 필요.
